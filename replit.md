# A.v.A — Anyone vs Anyone

**Live (production):** https://AnyoneVsAnyone.replit.app

## Overview

A mobile-friendly web app where users pick two teams of fictional characters and simulate dramatic round-by-round fight outcomes. Includes a character database, fight history, and the ability to add new characters.

## Stack

- **Monorepo tool**: pnpm workspaces
- **Node.js version**: 24
- **Package manager**: pnpm
- **TypeScript version**: 5.9
- **Frontend**: React + Vite (artifacts/fight-club), with Tailwind CSS v4 and Radix UI
- **API framework**: Express 5 (artifacts/api-server)
- **Database**: PostgreSQL + Drizzle ORM
- **Validation**: Zod (`zod/v4`), `drizzle-zod`
- **API codegen**: Orval (from OpenAPI spec)
- **Build**: esbuild (CJS bundle)

## Features

- Browse a roster of 956+ characters from 104+ universes (includes all 45 US presidents + 55 other Historical figures = 100 Historical characters)
- **Daily lineup**: 10 curated matchups posted every day at **8:00 PM ET** (rolls over via `America/New_York`, DST-aware — see `artifacts/api-server/src/lib/dailyPool.ts` `getDailyDateString`). Pool is **300 entries** (expanded from 202 — added 98 marquee matchups drawn from the full 1,208-character roster to deepen every themed bucket). Selection is **day-of-week themed by matchup concept** via `artifacts/api-server/src/lib/dailyThemes.ts`: Sun=**SHOWDOWN SUNDAY** (heroes vs villains, 55), Mon=**MARVEL vs DC MONDAY** (pure cross-company, 61), Tue=**TEAM-UP TUESDAY** (4+ char team brawls, 40), Wed=**WORLDS COLLIDE WEDNESDAY** (cross-franchise crossovers, 70), Thu=**THROWDOWN THURSDAY** (villain-vs-villain + horror icons, 65), Fri=**FACE-OFF FRIDAY** (1v1 same-universe rivals/mirror matches, 146), Sat=**STREET-LEVEL SATURDAY** (grounded fighters: boxing, MK, SF, John Wick tier, no cosmic, 45). Bucket sizes in parens give the no-repeat cycle length: Fridays = 14.6 weeks before any rival pairing repeats; Saturdays = 4.5 weeks; smallest bucket (Team-Up Tuesday) = 4 weeks — every day now has at least a month of unique matchups. Each entry is classified ONCE in `ENTRY_THEMES` (a baked-in `Record<id, ThemeKey[]>` map, ~202 entries) using character role (hero/villain by curated name list) + universe family (marvel/dc/anime/gaming/horror/street/historical from DB) + team size; classification is a build-time-style script, NOT runtime DB lookups, so the request path stays DB-free. An entry can live in multiple buckets (e.g. `avengers-vs-justice-league` = marvel_vs_dc + team; `sub-zero-vs-scorpion` = throwdown + rivals + street). Each bucket is pre-shuffled with a deterministic per-theme mulberry32 seed; daily lineup walks `DAILY_LINEUP_SIZE` entries through the bucket at `offset = (weekIndex * 10) % bucketSize` — **every matchup in a theme bucket appears exactly once before any repeat on that day-of-week**. A small per-day mulberry32 reshuffle varies display order. `getThemedDailyMatchupsForDate` falls back to filling from the wildcard bucket (full pool, safety net) if any themed bucket ever ends up <10. `GET /api/daily` returns `theme: { key, label, blurb }` alongside `matchups`; frontend header (`artifacts/fight-club/src/pages/daily.tsx`) replaces the static "Daily Matchups" title with `theme.label` + italic blurb. Lineup-stability invariant is unchanged — `ensureDailyRows` still locks the first materialized rows for a date by serial PK; the themed selector only runs on dates that have no rows yet. To add a new matchup: append to `DAILY_POOL` AND add a `ENTRY_THEMES[id]` entry (omitted entries fall to wildcard-only).
- **Lineup stability invariant**: once a date has any rows materialized in `daily_matchups`, those rows ARE the canonical lineup for that date — even if `DAILY_POOL` is later edited. `ensureDailyRows` sorts returned rows by the serial PK (`row.id` ASC = insertion order), NOT by recomputing `getDailyMatchupsForDate(date)`, so appending to the pool never reshuffles existing dates. `POST /api/daily/pick` also validates `matchupId` against the materialized rows (via `ensureDailyRows`), not the fresh canonical shuffle, so a mid-day deploy can't 404 picks for IDs the client already saw via GET.
- **Next-drop countdown**: home tile (when all 10 picks resolved) and Daily page subhead show "Next drop in Xh Ym" via `useNextDropCountdown`. DST-correct — `msUntilNextDailyRollover` picks the ET 20:00 UTC instant by trying both `-04:00` (EDT) and `-05:00` (EST) candidates and choosing whichever formats back to "target date 20:00" in ET. Re-ticks every 30s (or every 1s under the final hour).
- **Canonical daily fight replay**: every user who picks a daily matchup sees the SAME cinematic battle (not just the first runner). `daily_matchups.fight_id` links the first persisted fight; `generating_at` is a claim-lock mirroring `challengesTable.generatingAt`. Flow in `POST /api/fights/stream`: (1) if `fight_id` set → `replaySavedFight` returns it; (2) else try atomic claim `UPDATE daily_matchups SET generating_at=NOW() WHERE date=? AND matchup_id=? AND fight_id IS NULL AND (generating_at IS NULL OR generating_at<NOW()-120s)`; (3) claim winner generates + writes `fight_id` back via `IS NULL` guard; (4) losers `waitForDailyFightId` poll every 1.5s for 120s, then replay or retake stale claim. Daily branch runs AFTER the PvP challenge branch and is gated by `!normalizedChallengeCode`; both endpoints reject payloads carrying BOTH `challengeCode` and `dailyMatchupId` with 400 (mutual exclusion). Daily requests force canonical params (`modifierId=null`, `upset=false`) so a tampered first-runner can't poison the canonical replay with a verdict-flip. Dangling `fight_id` (linked fight row was deleted) is detected and cleared so the next picker regenerates instead of getting "saved fight not found" forever. Frontend: the `WATCH FIGHT` (gold, post-resolution) / `RUN THE FIGHT` (red, pre-resolution) CTA on `MatchupCard` is now shown to any user who picked, not only unresolved.
- **WHY? breakdown panel**: on resolved + picked daily matchups, a small `WHY?` button next to the WON/LOST pill expands an inline gold-bordered panel pulling the cached Stage-1 verdict from `fight_cache` via `GET /api/daily/matchup/:matchupId/breakdown` — shows difficulty/fight-type/win-rate pills, TURNING POINT, WHY THEY WON, KEY FACTORS, LOSER'S BEST MOMENTS. Zero AI cost (cache-only). Spoiler-gated: requires sign-in + a pick row for TODAY's date + this matchup (not "ever picked this matchup", which would leak via the 20-day rotation), and the matchup must be in today's materialized lineup. One-shot fetch with state cache; re-entry blocked while loading so rapid taps can't spawn duplicate requests.
- **Perfect-day badge & share**: when a signed-in user goes 10/10 on the day, a gold `PerfectDayBanner` appears atop the matchup list with a SHARE button that generates a 1080×1350 PNG on-canvas (no deps) and opens the OS share sheet via `navigator.share({ files })` on file-capable mobile, falls back to text-only share, then to a download. Trigger is purely client-side from existing `daily.matchups` (resolved+correct counts).
- Select up to 5 characters per team (Team 1 and Team 2)
- Simulate fights with cinematic AI narratives — phase-based (opening/escalation/turning point/finish) driven by each character's v3Profile (abilities, weapons, gadgets, combatStyle, battleIQ, temperament, finishers)
- Tier-calibrated outcomes (Cosmic → Street) using exponential 0-10M power stats; stronger always wins
- v3Profile jsonb column populated for 633/735 characters from PDF roster v3
- AI narrative follows user's cinematic spec: SETTING / ENTRANCE / FIGHT PHASES / RESULT / WHY THEY WON
- WHY THEY WON uses AI-generated text (5 parsed sentences), falls back to stat-computed bullets if AI returns nothing
- Re-read full match feature in History tab — expands round-by-round narrative with arenaIntro and intro text
- FAVES pill is on its own pinned row above the scrollable universe filter pills (won't get scrolled out)
- Debate Room has a "Developer Legends" tab featuring Chris Henry & Troy Wilson with the Betrayal Protocol matchup
- Developer Legends: Chris Henry and Troy Wilson are seeded at max stats (99999 all stats). When on opposing teams, the AI override makes them refuse to fight each other and brutally betray their partners to win together
- View fight history; add/delete characters; universe breakdown stats; character leaderboard
- **Ghost-hand tutorial (first run)**: five-step choreography in `ghost-hand-tutorial.tsx` — pick champion → pick same-universe synergy partner (auto-appends to Team 1 via `tutorialSynergyPick` memo, then highlights the synergy strip so the user sees a real `<UNIVERSE> UNITY +8%` pill) → pick nemesis → point at the modifier chip (caption "Chaos Rules · Twist Fate", no tap — kept first-run fast) → linger on FIGHT. Synergy partner is the first iconic name from `ICONIC_TUTORIAL_NAMES` whose `universe` matches the champion's; if none exists the step silently no-ops. `data-tutorial-id="modifier-chip"` wraps `ModifierTrigger`; `data-tutorial-id="synergy-strip"` wraps the synergy pill row. `onPickForTeam(character, slot, append)` now supports append for the synergy step without clobbering the champion. FightScreen has `autoStartNarration` — when true (only the first tutorial-staged fight, gated by `tutorialStagedRef.current` at the moment the modal opens), the round-1 reveal auto-fires `playNarration()` so brand-new users hear the AI voice without finding the Play CTA. The auto-start effect is declared AFTER the round-switch effect on purpose (React runs effects in declaration order, and round-switch wipes `narrationActiveRef` on every visibleCount tick), gated to `visibleCount===1 && activeRoundRef.current===0` so it can't arm narration for the wrong round. The FIGHT-button tap that opened the modal IS the iOS audio-unlock gesture.
- **PvP Challenge Links**: CHALLENGE button on home page (next to FIGHT/RANDOM) creates a shareable 6-char code. Creator sees a share box + waiting screen (`/challenge/<code>?creator=1`). Opponent opens the plain URL, picks their team, and clicks ACCEPT & FIGHT
- **Blind Pick**: same flow but challenger's team is hidden (shown as ??? silhouettes) until opponent locks in — then both teams reveal and the fight auto-starts after a 1.6s reveal flash

## AI Narrative (OpenAI via Replit proxy)

- Uses `@workspace/integrations-openai-ai-server` (OpenAI SDK configured with `AI_INTEGRATIONS_OPENAI_BASE_URL` + `AI_INTEGRATIONS_OPENAI_API_KEY`)
- Model: `gpt-5-mini` with `stream: true` — streaming is REQUIRED; non-streaming requests return empty content
- `max_completion_tokens` must be 8192 — proxy rejects lower limits with `finish_reason: length` + empty body
- Format: `=== ARENA ===` intro + `=== ROUND N ===` sections parsed by regex in `generateAINarrative()`
- Fight rounds capped at 6–8 to keep AI generation under 80 seconds
- Falls back to template-based narratives if AI times out or errors
- Narrative generation is parallelized for fights with 3+ rounds: Call A writes SETTING + ENTRANCE + first half of rounds; Call B writes second half + RESULT + WHY THEY WON. Both calls share the same character profiles, locked verdict, resolution brief, and HP timeline. Each is wrapped in PARTIAL OUTPUT MODE framing so the model emits only the requested sections starting with the first === marker. Outputs are concatenated; existing parseSections (first-wins on duplicates) merges them. Roughly 25–40% wall-clock reduction with no quality change.
- SSE streaming endpoint `POST /api/fights/stream` emits sections as they finish (init → section per `=== MARKER ===` block → complete). `aiTextWithTimeout` accepts an `onDelta` callback; `makeSectionStreamer` watches the streaming buffer via `parseSections` and fires `onSection(name, content)` as soon as the next marker appears (one-ahead boundary detection). The frontend consumes via `useSimulateFightStream` (fetch + ReadableStream — `EventSource` can't POST); result builds progressively and `FightScreen.revealOne` polls every 200ms for the next round's narrative, with a watchdog that bypasses the wait once `result.id !== -1` (complete event arrived → server fallbacks guaranteed). Same gpt-4o, same prompts, same parallel split — perceived time drops from ~50s of spinner → first content in 6–10s.
- PvP challenge sync: when a fight is part of a challenge (request includes `challengeCode`), both players see the **same** narrative instead of independently generating different ones. Mechanism: `challengesTable` has `fightId` (nullable int) and `generatingAt` (nullable timestamp). On `POST /api/fights/stream` with a `challengeCode`: (1) if `challenge.fightId` is set → instantly emit `init`+`complete` from `fightsTable[fightId]`. (2) Otherwise try atomic claim — `UPDATE challenges SET generating_at=NOW() WHERE code=? AND fight_id IS NULL AND (generating_at IS NULL OR generating_at < NOW()-120s)`. (3) Whoever wins the claim runs the normal AI stream and writes `fight_id` back when the fight row is persisted. (4) Whoever loses the claim polls every 1.5s for `fight_id` to appear (max 120s), then replays. Stale-lock recovery means a crashed/aborted generation doesn't deadlock the challenge. `fightsTable.whyWon` (jsonb) was added so the replay path can show the same "Why They Won" panel — previously only `summary`/`rounds`/`arenaIntro`/`intro` were persisted. The frontend hook needs no changes; it already treats `complete` as canonical and fills the UI immediately on the replay path.
- Verdict-only cache: `fightCacheTable` stores who wins (and the resolution brief — difficulty, fightType, keyFactors, turningPoint, loserShowcase, winnerProof) keyed by canonical sorted team IDs, so rematches between the same characters always end the same way unless Upset Mode is on. The narrative itself is **always regenerated** on every fight so each one reads as a unique story — variety is the whole point. (An earlier experiment cached the full narrative payload for sub-100ms rematches, but it was reverted because users want every fight to feel new. The `narrative` jsonb column on `fightCacheTable` is still present from that experiment but is no longer read or written.)
- Token-level streaming: `makeSectionStreamer` also accepts an optional `onSectionDelta(name, append)` callback that fires per AI chunk for the currently in-progress section, with trailing partial markers (`=== ROU…`) stripped. The SSE route emits these as `delta` events; the hook accumulates per-section live buffers and flushes via `requestAnimationFrame` (~60fps cap) so the UI types out narrative as the AI writes it. `WHY THEY WON` skips delta streaming since it parses into a numbered list. The canonical `section` event still fires at marker boundaries and overwrites whatever the deltas built. With this on, ROUND 1 starts appearing at ~15s instead of being dropped as a wall of text at ~43s — same total time, same content, dramatically less static screen time.
- Loader→narrative handoff: the hook exposes a `streaming` flag (true on first delta or section), and `home.tsx` uses `isPending && !streaming` for `isSimulating` so the cinematic FightLoadingSequence keeps playing all the way until real text starts arriving — no more static gap between init (~7s) and first text chunk (~12s). The 7 phases tick every 1400ms (was 3200ms) so they all play through within the typical pre-text window, and the last phase holds rather than looping.
- Round reveal pacing: `scheduleNarrativePause` was tightened from 400/1400/1900/1400ms to 250/900/550ms (turning point still gets the extra beat), so the auto-reveal stagger doesn't feel baggy when text is already in the buffer. The reveal loop also got a defensive watchdog: it always polls 150ms for the round's narrative to be present, but if the stream has been complete for >2.5s and a round is still empty, it reveals anyway so the UI cannot strand on an empty box.
- Manual round progression: the auto-reveal loop was replaced with a user-controlled flow. After SETTING + COMBATANTS ENTER finish streaming, a "Begin Match →" button appears. Clicking it reveals Round 1; once that round's narrative is fully complete, a "Next Round →" button appears below it; repeat for each round. After the last round's narrative is complete (and `whyWon`/summary have arrived), the winner reveal banner becomes available. The hook tracks `completedSections: Set<string>` (UPPERCASE section names that have received their canonical `section` event, plus all of them on `complete` for cache-hit safety), and FightScreen uses that set to decide when each gating button is allowed to render — buttons never appear mid-stream. "Skip" stays in the bottom bar throughout the fight and jumps straight to the winner banner; it's hidden once the banner is showing (nothing left to skip).

## Auth (Clerk, optional)

- Provisioned via `setupClerkWhitelabelAuth`. Env: `CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY`, `VITE_CLERK_PUBLISHABLE_KEY`. Proxy middleware (prod-only) at `artifacts/api-server/src/middlewares/clerkProxyMiddleware.ts`.
- API: `clerkMiddleware()` mounted in `app.ts`. Helpers in `src/lib/auth.ts` — `getOptionalUserId(req)` for guest-permissive routes, `requireAuth(req,res)` for protected routes.
- Schema: `fightsTable.userId` (text, nullable) and `challengesTable.creatorUserId` (text, nullable). Guests still write — `userId` stays null. Migration `0001_add_user_attribution.sql` (uses `IF NOT EXISTS` so it's idempotent against db:push'd dev DBs).
- Tagging: `POST /fights` and `POST /fights/stream` capture `userId` via `getOptionalUserId`; challenge create captures `creatorUserId`.
- Personal endpoints (signed-in only, return 401 for guests): `GET /api/me/fights` (last 100 fights) and `GET /api/me/stats` (totals + win split + per-character used/wins). Called directly via `fetch(..., { credentials: "include" })` — not in `openapi.yaml` (could be added later for typed coverage).
- Frontend: `App.tsx` wraps in `ClerkProvider` with `dark` theme + `clerkAppearance` (magenta/red brand, Bebas Neue/Rajdhani fonts). Routes: `/sign-in/*?`, `/sign-up/*?`, `/profile`. `Layout` has a 44px top header with `AvaLogo` + sign-in button (signed-out) / avatar→profile button (signed-in). Sign-in/up routes hide all chrome.
- `/profile` page: signed-out shows a sign-in CTA; signed-in shows name/avatar, sign-out button, three stat tiles (fights / T1 / T2 wins), win-split bar, top-6 favorite fighters with medals + win%, recent 10 matches.
- Vite needs `tailwindcss({ optimize: false })` and `@layer theme, base, clerk, components, utilities;` declared in `index.css` before tailwind import so Clerk's stylesheet wins inside our shell.
